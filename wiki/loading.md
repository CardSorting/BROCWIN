# PE loading, DLL lifecycle and Windows contracts

[Wiki home](README.md) · [Implementation and tests](generated/INDEX.md#loading)

The shared PE loader maps original sections, imports, relocations and TLS metadata. `lib/dll-loader.js` resolves dependency order and executes original DLL entry points. Platform adapters generated by `platform_dlls.py` expose PE export names/ordinals and route x86 import jumps into Wasm handlers; these are reconstructed Windows interfaces, not recovered game DLL source.

The original client sometimes parses PE export tables itself, so host-only name lookup is insufficient. Incorrect ordinals previously corrupted the guest stack. Each new API must match its x86 argument count, return/error convention and pointer ownership. `src/api_table.json` is append-only; the dependency build validates dispatch/hash freshness and stack cleanup. Strict initialization is required on every loader/backend.

The shader-validator factory executes a locally derived component of installed 32-bit Microsoft D3D9 code. Its original mapped sections remain byte exact; a reconstructed initializer and export directory make the bounded component callable. This is separately attributed platform code generated locally, not an original fork component or a replacement shader compiler. See the native reference and validator tests.

## Lifecycle and TLS repair

The loader now reserves a distinct static TLS index per module, copies relocated initialized bytes plus zero-fill into separate registered-thread blocks, and publishes a DLL only after success. New threads receive loaded-module TLS before original attach entry points. `AddressOfIndex` is not a per-thread pointer. The original EXE, MFC42 and msvcrt were observed at indices 0, 1 and 2 on the sealed passing build.

New thread-attach sequences run as guest code through the normal scheduler. The old synchronous callback runner failed when msvcrt waited for a critical section (`033829`). Guest thunks preserve the thread procedure's stack and parameters, consult live `DisableThreadLibraryCalls` flags, and permit normal waits. Suspended threads begin notifications when runnable.

## Failure and repair procedure

For an initializer failure, retain the executing module/address, last error, halt/yield reason, callback order and mapped image/TLS metadata. Check `test-dll-init-order.js`, `test-dll-thread-attach-wait.js`, `test-pe-dll-static-tls.js`, and `test_platform.cjs`. The TLS regression executes x86 `FS:[0x2c]` accesses in cooperative and Worker backends, covering late loading, zero-only templates, sparse relocation, distinct blocks, reused slots and malformed-index rejection. Do not infer allocation-failure rollback correctness from tests that never induced OOM.

Open contracts include nonempty PE TLS callbacks, over-aligned templates, TLS reclamation at unload, and a complete common loader lock spanning process loads/thread creation/thread detach. Retained TLS-vector registry entries can belong to exited threads. The earlier collision of DLL/EXE indices is proven; execution of the suspected colliding MFC write on the failing build was not observed.
